# 模块一：cli-chatbot

基于 DeepSeek API 的命令行流式多轮对话工具，内置**错误重试、token 成本核算与上下文管理**。
纯 Python 标准库 + OpenAI 兼容 SDK，无其他框架依赖。

## 功能

- **流式输出**：逐字打印，首字响应快，不等全文
- **多轮对话**：完整历史管理，失败自动回滚，不会留下"有问无答"的脏历史
- **智能重试**：错误三分类（可重试 / 致命 / 未知），指数退避 + 随机抖动；已开始输出的内容不重试
- **成本核算**：区分输入/输出、缓存命中/未命中，识别高峰与空闲时段（单价差 2 倍），每轮实时记账，支持月成本预估
- **上下文管理**：滑动窗口裁剪历史（system 永不裁、问答对不切开），配合前缀缓存降低单会话成本约 26%
- **自动存档**：每轮落盘，崩溃不丢对话；支持手动存档 / 读档

## 快速开始

```bash
# 1. 克隆并安装依赖
git clone https://github.com/itxiong184/cli-ai-chatbot.git
cd cli-ai-chatbot
python -m venv .venv
.venv\Scripts\activate        # Windows；macOS/Linux 用 source .venv/bin/activate
pip install -r requirements.txt

# 2. 配置密钥
copy .env.example .env        # 然后编辑 .env，填入你的 API Key

# 3. 运行
python chatbot.py             # 交互式聊天
python chatbot.py --selftest  # 本地逻辑自测（不联网、不花钱）
python chatbot.py --demo      # 单轮验证接口连通性
```

API Key 在 [DeepSeek 开放平台](https://platform.deepseek.com) 申请，充值 10 元即可支撑数千次对话。

## 使用命令

| 命令 | 作用 |
|---|---|
| `/cost` | 账本：调用次数、单次均价、累计费用、月成本预估 |
| `/clear` | 清空对话历史（system 保留，账本不清零） |
| `/history` | 查看当前历史条数 |
| `/save` / `/load` | 手动存档 / 读档（每轮成功后也会自动存档） |
| `/quit` | 退出，自动存档并打印账单 |

## 设计要点

**1. 流式响应中主动获取用量**
流式模式下服务端默认不返回 token 用量，需显式传 `stream_options={"include_usage": True}`；且携带用量的末帧 `choices` 为空列表，必须先取 usage 再判空，否则会在输出完成后抛 `IndexError`。用量缺失时按字符数估算兜底，并在界面明确标注"估算值"——计费场景不使用估算数。

**2. 流式重试的副作用控制**
普通请求失败可直接重试；流式一旦开始打印，已显示的内容无法撤回，重试会导致输出拼接错乱。因此用状态标记区分：未打印 → 走指数退避重试；已打印 → 立即失败并回滚历史，本轮不计入。

**3. 成本结构分析与降本**
多轮对话全量重发历史导致成本近似平方增长。通过滑动窗口裁剪 + 稳定前缀可缓存，单会话成本由 0.0228 元降至约 0.0169 元（**降 26%**）。裁剪实现保证 system 提示永不丢弃、问-答对不分离。实测同一调用在高峰时段（工作日 9–12 / 14–18 点）成本为空闲时段的 2 倍，批量任务应错峰调度。

## 实测数据

| 指标 | 数值 |
|---|---|
| 单轮对话成本（高峰） | 约 0.5–1.0 厘（0.0005–0.001 元） |
| 单次会话成本（6 轮） | 约 0.017 元 |
| 首字响应 | 约 1 秒 |
| 上下文窗口 | 保留最近 8 轮 + system |

# 模块二：resume-extractor

把一段自由文本（简历片段、口语化自我介绍、招聘启事）抽取成固定结构的 JSON，供入库、筛选、打分等下游程序使用。

## 为什么需要它

聊天模式的输出给人看，抽取模式的输出给程序用。`"郑州轻工业大学，本科，会 Python"` 没法做筛选；`{"school": "...", "degree": "本科", "skills": ["Python"]}` 可以直接进数据库。

## 数据契约（schema v2.0）

```json
{
  "name": "string|null",
  "phone": "string|null",
  "email": "string|null",
  "city": "string|null",
  "education": [
    {"school": "string", "major": "string|null",
     "degree": "专科|本科|硕士|博士|null", "graduation_year": "string|null"}
  ],
  "skills": ["string"],
  "years_experience": "number|null",
  "projects": [{"name": "string", "tech": ["string"], "summary": "string|null"}]
}
```

`education` 和 `projects` 是**对象数组**：一个人可能有三段学历、四个项目，扁平结构只能存一个，其余信息在抽取阶段就永久丢失了。

## 五层校验

| 层 | 检查什么 | 能挡住什么 |
|---|---|---|
| **0. 输入预检** | 调用前扫一遍原文：有没有姓名锚点？有没有被误认的校名缩写？有没有第三方联系人？全文到底有没有手机号？ | 把错误在发生前消解，而不是事后补救 |
| 1. 结构 | 字段是否齐全、类型是否正确 | 模型改字段名、漏字段 |
| 2. 格式 | 手机号 11 位、年份 4 位、学历在枚举内 | 脏值污染下游 |
| 3. 依据 | 抽出的值能否在原文找到 | 编造（幻觉） |
| 4. 归属 | 值所在句子里，它前面有没有"联系人/家属/推荐人" | 张冠李戴（HR 的电话安到候选人头上） |
| 5. 角色 | 姓名是否是学校名的一部分、是否出现在"…届"结构里 | 把"郑轻"当成人名 |

第 3 层挡不住第 4 层的问题：HR 的号码**确实在原文里**，回溯校验必然通过，但号码不属于候选人。这类错误叫归属错误，必须单独检测。

第 0 层是唯一"不花钱"的一层：预检结论以几句额外的约束追加到 system prompt 末尾（不是开头，否则每条样本的前缀都不同，前缀缓存全废）。

校验不通过时，把问题清单回灌给模型让它自己改一次（self-repair）。**但"不确定"与"错误"必须分开**：只有确定错误才允许自动修复，判不出归属的字段只标注、不清空——校验器的误报会比原错误更难发现。

## 快速开始

```bash
python preflight.py                    # 输入预检演示（纯正则，不联网）
python extractor.py --dry              # 只看将要发送的 prompt，不花钱
python extractor.py                    # 跑内置 4 个样本
python extractor.py --file 我的简历.txt  # 抽你自己的
python test_extractor.py               # 纯函数单元测试（24 项，不联网）

python batch_extract.py                # 批量抽取（并发 6 + 断点续跑）
python batch_extract.py --no-hints     # A/B 对照：不注入预检提示
python eval_resume.py                  # 打分：字段级 / 条目级 / 完全正确率
python eval/build_v3.py                # 重新生成评测集（含标注变更留痕）
```

## 评测结果（60 条人工标注，schema v2.1）

| 指标 | 数值 |
|---|---|
| 完全正确率 | **98.3%**（59/60，8 个字段全对才算对） |
| 字段平均准确率（macro） | 99.6% |
| 技能集合 P / R / F1 | 99.7% / 99.4% / 99.5% |
| 学历条目 P / R / F1 | 100% / 100% / 100%（子字段 240/240） |
| 项目条目 P / R / F1 | 100% / 100% / 100%（子字段 45/46） |
| 批量吞吐 | 60 条 / 12 秒（并发 6，约 0.2 s/条） |
| 单条成本 | 约 1.2 厘（62 次调用 / 60 条，多出 2 次是自修复；高峰时段） |

### 输入预检的 A/B 对照（同一批 60 条，只改一个变量）

| 组 | 完全正确率 | macro | 差异样本 |
|---|---|---|---|
| 注入预检提示 | 98.3%（59/60） | 99.6% | — |
| 关闭预检提示 | 96.7%（58/60） | 99.4% | r33：丢失整条学历段 |

**结论要说得克制**：n=60 上只差 1 条，不能声称"显著提升"。但差异恰好落在预检针对的那个失败模式上（"我是郑轻 2027 届的"——带提示时模型把"郑轻"归入 `education[].school`，不带提示时整段被丢弃）。机制上成立，统计上不成立，这两句话必须分开说。

另有 3 条（r23 / r25 / r48）输出有差异但不影响得分，差在 `summary` 文本与项目顺序——`summary` 目前不参与打分，属于评测口径的已知空白。

## 迭代记录：同一份数据，宏观准确率 94.7% → 98.4%

第一轮跑完发现两个问题，都不是"模型不行"：

1. **我自己写的归属检测误报**，把 r10 / r32 两条正确的手机号判成干扰，自修复又把它改成了 `null`——校验器的误报会主动污染数据，比漏检更危险。修法：窗口从"前后 25 字"收窄到"同一句内、且词在值之前"。修复后这两条立刻恢复，`phone` 字段回到 100%。
2. **`skills` 的定义没写清**：项目里提到的技术算不算技能？没说，于是模型抽了、我标的是空。把规则写明（全文技术关键词，允许与 `projects[].tech` 重复）并重标 10 条后，`skills` 从 75% 升到 95%。

同时补了 `test_extractor.py`：`validate()` 是纯函数，用单元测试钉住行为；只有模型那部分才需要评测集。

## 迭代记录：40 条 → 60 条，92.5% → 98.3%

第三轮做了三件事，全部围绕"让校验更早、更准"：

1. **新增输入预检（`preflight.py`）**。规则是"单个信号不判决，两个独立信号交叉才报警"：一个片段只有同时满足"出现在 `我是…的 / …届 / 毕业于…` 结构里"和"全文没有姓名锚点"，才被判定为学校简称。这条约束的直接来源，就是上一轮"校验器误报把正确数据改成 null"的事故。
2. **skills 口径改为"具体技术专名"**（v2.1）。剔除学科/方法/角色词（数据结构与算法、统计建模、后端开发），并识别"技术名 + 领域词"的拼接短语（`Python 自动化测试` → `Python`）。同一字段前后改了两版——第一版为了让分数好看而迁就模型措辞，那是错的；第二版才把规则本身写清楚。
3. **评测集扩到 60 条**，新增 20 条专门打失败模式：英文简历、表格型、校名缩写无姓名锚点、专升本两段、本硕同校、推荐人干扰、项目无名称、全文无具体技术词。

**这一轮的方法论改进**：做了真正的单变量 A/B（`--no-hints`），而不是像上一轮那样三个变量一起改、无法归因。

## 踩坑记录

**1. `.gitignore` 不支持行内注释**
写了 `.env   # API Key 在里面`，git 把整行当成文件名，规则静默失效，`.env` 差点被推上公开仓库。注释必须独立成行，且 `git add` 之后一定要看 `git status`。

**2. 流式响应的末帧 `choices` 是空列表**
带 usage 的那一帧没有内容，习惯性写 `chunk.choices[0]` 会 `IndexError`，而且崩在输出完成之后，看起来像"答完了但程序报错"。顺序必须是：先取 usage，再判空。

**3. `"2027" in text` 这种检查会骗人**
邮箱 `liming2027@163.com` 里也有 `2027`。年份校验必须用词边界 `(?<![0-9A-Za-z])2027(?![0-9A-Za-z])`。

**4. 校验器的误报会通过 self-repair 污染数据**
把"没有依据的字段必须为 null"写进修复提示，等于给模型一个清空字段的许可。检测器一旦误报，正确的数据就被改成 null。修复提示要交回判断权："确实错的才改，原文写明的要保留"。

**5. 预检本身也是启发式，照样会误报**
第一版预检把 `我是郑轻` 整串当成候选校名（正则的 `{2,4}` 可以从"我"开始匹配），又把 `2023 届…电话 13800138000` 的数字粘成一个长串导致"有手机号却判成没有"。修法：候选片段加前缀/包含词过滤；手机号改为"先按连续数字块切开再匹配"。**每一层新增的检测，都要配一条自己的误报回归测试。**

**6. 评测集饱和比准确率低更麻烦**
60 条上 98.3%，说明这套题已经不能区分"好"和"很好"了。下一步不是继续加同类样本，而是加更难的分布（模糊、缺字段、多实体、长文档），或者把指标改严（现在标量比对是子串匹配，`上海` 能匹配 `上海市浦东新区`）。**分数接近满分时，要怀疑的是尺子，不是被测对象。**
